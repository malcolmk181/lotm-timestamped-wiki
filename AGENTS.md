# Project conventions

## Commits
- Conventional Commits only (`feat:`, `fix:`, `docs:`, `chore:`, `test:`,
  `refactor:`, `build:`). Scope optional, e.g. `feat(data): extract ch 4-7`.
- Commit early and often; push after each meaningful change.

## Tooling
- Use `uv` for Python (`uv run python build.py`), never bare `python3`.
- `build.py` must remain stdlib-only (tomllib, json, pathlib). Do not add a
  runtime dependency without a good reason and a README update.

## Data authoring (the important part)
- **No spoilers.** A fact may only cite/mention what is knowable by its own
  `established_at` chapter. Reversals are authored at the chapter that reveals
  them, not before.
- **Always cite a source** (`chapter` required, `quote` strongly encouraged).
  Never invent a fact or a quote — work from the actual text in
  `../LOTM-Reader/chapters/lotm/`.
- **Author only forward pointers.** Write `refines` / `supersedes` on the newer
  fact; never hand-set `revoked_at` (build.py derives it).
- **Be noisy and detailed.** More small facts > fewer big facts. Prefer many
  specific claims over one umbrella claim; this is what makes refinements and
  overturns meaningful.
- **Use `certainty` honestly.** `fact` = shown on the page; `inference` =
  strongly implied; `hypothesis` = a character's explicit guess;
  `speculation` = loose/uncertain.
- Entity `type` and fact `certainty` use controlled vocabularies — extend them
  deliberately (and update `build.py`'s allowlists), not ad hoc.
- **No free-text on entities.** Entities carry only structured, schedule-safe
  fields (id, name, type, first_seen, aliases). Any descriptive text is a fact
  — timestamped and sourced — never a bare `summary` string, which would leak
  later knowledge backward. (This was a real bug found in the Evernight Goddess
  summary leaking "seven orthodox gods" into chapter 1.)

## Generated files
- `site/data/*.json` are generated by `build.py`. Regenerate and commit them
  after any `data/` change so the static site stays current.
